## Initial problem

The user runs SillyTavern remotely (server not under user control) and opens it in an Android browser. The Android phone has **MultiTTS** installed and usable as a system TTS engine.

Observed mismatch:

- Android/system reading can use MultiTTS.
- SillyTavern's built-in `System` TTS did not reliably use MultiTTS.
- OPPO's built-in TTS settings did affect SillyTavern System TTS.

Investigation of SillyTavern showed that `System` uses browser Web Speech (`window.speechSynthesis`), not a direct Android `TextToSpeech` call. Therefore Android's default TTS engine and browser-exposed voices are not guaranteed to match.

## Remote SillyTavern architecture

Important distinction established:

```text
Remote server serves the SillyTavern page
              |
              v
Android Chrome executes extension JavaScript
              |
              v
127.0.0.1 means the Android phone
              |
              v
MultiTTS APK
```

A browser-side SillyTavern provider can therefore reach the phone's localhost even though the SillyTavern backend is remote.

A server-side proxy provider would not work with `127.0.0.1`, because localhost would then mean the remote server.

## SillyTavern queue and splitting behavior reviewed

Current SillyTavern TTS core has:

- `ttsJobQueue`
- `audioJobQueue`
- one `audioElement`
- `audioQueueProcessorReady`
- current job is completed when audio `ended` fires

A direct URL string is stored in `audioJobQueue`, and the actual URL is assigned to the audio element when that queue item is processed.

This means actual local TTS media loads are naturally serialized by playback.

### Built-in Narrate by paragraphs

Current core behavior:

```js
if (!extension_settings.tts.narrate_by_paragraphs) {
    ttsJobQueue.push(clone);
    return;
}

const lines = clone.mes.split('\n');
...
ttsJobQueue.push({ ...clone, mes: line });
```

Therefore it already splits on newline paragraphs, but does not protect against a single extremely long paragraph.

## Follow-up: Android background lifecycle, native TTS limits, and independent-player boundary

The user requested a broader investigation before further development, specifically asking whether the reliability problems are native SillyTavern/mobile-browser problems and whether a larger independent TTS/player extension would be preferable to continuing to depend on SillyTavern's TTS core.

### User-observed behavior

- Leaving the SillyTavern browser / returning to Android home can sometimes interrupt text generation.
- TTS is even more likely to stop in the background.
- After interruption, pressing the SillyTavern TTS control can restart narration from the beginning.

### Browser lifecycle evidence

Chrome Page Lifecycle documentation confirms:

- switching apps on mobile can move the page to `hidden`;
- hidden pages can later become `frozen` or `discarded`;
- in `frozen`, JavaScript timers and fetch callbacks do not run;
- in `discarded`, no page JavaScript runs at all;
- mobile operating systems can stop applications to reclaim resources.

Reference:
https://developer.chrome.com/docs/web-platform/page-lifecycle-api/

Chrome documents that active audio playback is one signal that makes a page less likely to be discarded, but this is not an absolute guarantee.

A separate Chrome timer-throttling article is important for interpreting "silence keep-alive" tricks: it says a silent audio track does **not** count as recent sound for its timer-throttling exemption.

Reference:
https://developer.chrome.com/blog/timer-throttling-in-chrome-88/

### SillyTavern official workaround: Silence Player

Official repo:
https://github.com/SillyTavern/Extension-Silence

Official SillyTavern content description:
"Adds a silence audio player to the extensions menu. Can help if the browser tab is being killed in a background."

Its implementation is intentionally simple: a looping HTML `<audio>` element loading a bundled `silence.m4a`.

Community reports found in 2025-2026 repeatedly suggest:

- Silence Player;
- unrestricted battery/background permission for the browser;
- floating-window/split-screen as a practical fallback;
- trying a browser that is less aggressively suspended.

Reports are mixed. Some say Silence Player helps with tab/app switching; others still see failures after a few minutes or on screen lock. Treat this as a low-cost mitigation, not a guaranteed fix.

### Why text generation itself can stop

Inspection of current SillyTavern backend source shows many provider routes bind upstream cancellation to the client request socket closing:

```js
const controller = new AbortController();
request.socket.removeAllListeners('close');
request.socket.on('close', function () {
    controller.abort();
});
```

Current source:
https://github.com/SillyTavern/SillyTavern/blob/release/src/endpoints/backends/chat-completions.js

This means that if Android/browser lifecycle actually closes the client request/socket, SillyTavern can deliberately abort the upstream model generation.

Therefore a TTS-only browser plugin cannot solve the background-generation problem. It only receives text if the generation survives long enough for the page to receive it.

### Why the TTS control restarts from the beginning

Current TTS core:
https://github.com/SillyTavern/SillyTavern/blob/release/public/scripts/extensions/tts/index.js

The playback control is intentionally implemented as **full stop**, not pause.

The reset path clears:

- `currentTtsJob`;
- `currentAudioJob`;
- `ttsJobQueue`;
- `audioJobQueue`;
- current audio time/source.

When idle, the same control queues the latest message again.

Official TTS docs also call this a **Stop** button:
https://docs.sillytavern.app/extensions/tts/

So restart-from-beginning after interruption is consistent with current SillyTavern behavior.

### Upstream gapless TTS issue confirms our queue analysis

Open issue:
https://github.com/SillyTavern/SillyTavern/issues/6031

The issue reports audible 0.3-0.5 second gaps between chunks and states:

- current core player is strictly sequential;
- next chunk is only processed after the current item emits `ended`;
- each `.src` swap causes a fresh decode / `canplay` wait on mobile;
- provider-side prefetch alone cannot remove the gap;
- SillyTavern already has an AudioContext/AudioWorklet PCM mechanism in `tts-webui.js` that could be generalized into core.

This is strong independent confirmation that our current direct-URL MultiTTS path is hitting a known player-level limitation, not merely a mistake in our splitter.

However MultiTTS's missing readable CORS response remains a special constraint. A PCM AudioWorklet solution needs readable bytes, while our page currently can only prove direct media loading.

### What an independent narrator/player extension could improve

A larger extension that does **not** use SillyTavern's native TTS player could listen for completed/updated assistant messages and own its own narration state.

Potential benefits:

- independent segmentation rules;
- pre-generation/preload window;
- ordered playback buffer;
- real pause/resume rather than full stop;
- remember chunk index and `currentTime`;
- retries and skip-on-error;
- explicit cancellation semantics;
- Media Session controls;
- diagnostic state that is not mixed into provider code.

This may be a cleaner long-term TTS product than continuing to bend the current native TTS queue around MultiTTS's direct-URL/CORS constraints.

But it has an important limit: it remains JavaScript in the same browser page. If Chrome freezes/discards the page, or Android kills the browser, the custom player is suspended too. Therefore it can improve **TTS continuity while the web runtime remains alive**, but cannot guarantee **background chat generation**.

### Native wrapper evidence

TauriTavern:
https://github.com/Darkatse/TauriTavern

Its Android design is relevant because it explicitly addresses this lifecycle boundary.

Documentation:
https://github.com/Darkatse/TauriTavern/blob/main/docs/AndroidDevelopment.md

Current design:

- first Chat Completion starts an Android `dataSync` Foreground Service;
- Rust `ChatCompletionService` owns the generation task/background lease;
- concurrent tasks share the foreground service;
- WebView only consumes results;
- documentation explicitly avoids tying native task completion to WebView callbacks because WebView can be suspended.

This is the kind of architecture required if background generation must be reliable across app switching/screen-off. It is qualitatively different from adding more JavaScript to a SillyTavern extension.

### Design implication for this project

Keep two layers separate:

**Layer A — thin MultiTTS provider**
- continue supporting the simplest proven SillyTavern integration;
- keep production provider minimal;
- use this when the user is happy with SillyTavern's player semantics.

**Layer B — optional independent narrator/player**
- only build if testing confirms native player gaps/restart semantics are unacceptable;
- own queue/resume/preload explicitly;
- do not claim it fixes browser background suspension.

If the requirement later becomes:

> generation and narration must both continue reliably with browser backgrounded / screen off

then a native app/wrapper or server-side persistent-job design is the relevant architecture. A larger browser-only TTS plugin is not sufficient.

### Immediate validation plan

Before creating the independent player:

1. Install/enable official Silence Player and start it.
2. Set browser battery/background permission to unrestricted where possible.
3. Set MultiTTS background/battery/keep-alive options where available.
