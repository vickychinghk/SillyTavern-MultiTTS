## Initial problem

The user runs SillyTavern remotely (server not under user control) and opens it in an Android browser. The Android phone has **MultiTTS** installed and usable as a system TTS engine.

Observed mismatch:

- Android/system reading can use MultiTTS.
- SillyTavern's built-in `System` TTS did not reliably use MultiTTS.
- OPPO's built-in TTS settings did affect SillyTavern System TTS.

Investigation of SillyTavern showed that `System` uses browser Web Speech (`window.speechSynthesis`), not a direct Android `TextToSpeech` call. Therefore Android's default TTS engine and browser-exposed voices are not guaranteed to match.

## MultiTTS forwarding interface discovered from the app

The app itself shows:

```text
转发器
语音合成接口( http://localhost:8774/forward )，GET参数：
text：要合成的文本
speed：语速，取值0~100
volume：音量，取值0~100
pitch：音高，取值0~100
voice：声音id，请求/voices接口获取所有发音人
语音列表接口( http://localhost:8774/voices )，无参数。
```

Direct phone-browser tests:

- `http://127.0.0.1:8774/voices` returns a long voice list.
- `http://127.0.0.1:8774/forward?... ` returns a playable/downloadable `forward.wav`.

This proved the local service itself was alive.

## Remote SillyTavern architecture

Important distinction established:

```text
Remote server serves the SillyTavern page
              |
              v
Android Chrome executes extension JavaScript
              |
              v
127.0.0.1 means the Android phone
              |
              v
MultiTTS APK
```

A browser-side SillyTavern provider can therefore reach the phone's localhost even though the SillyTavern backend is remote.

A server-side proxy provider would not work with `127.0.0.1`, because localhost would then mean the remote server.

### TTS WebUI

SillyTavern TTS WebUI performs a browser-side request, which is architecturally compatible with a local phone service.

However its protocol is POST JSON / OpenAI-like, while MultiTTS documents GET query parameters on `/forward`. Therefore it is not a direct protocol match.

### OpenAI Compatible

Current SillyTavern implementation routes this through SillyTavern's backend, making it unsuitable for a localhost service on the user's phone.

## SillyTavern queue and splitting behavior reviewed

Current SillyTavern TTS core has:

- `ttsJobQueue`
- `audioJobQueue`
- one `audioElement`
- `audioQueueProcessorReady`
- current job is completed when audio `ended` fires

A direct URL string is stored in `audioJobQueue`, and the actual URL is assigned to the audio element when that queue item is processed.

This means actual local TTS media loads are naturally serialized by playback.

### Built-in Narrate by paragraphs

Current core behavior:

```js
if (!extension_settings.tts.narrate_by_paragraphs) {
    ttsJobQueue.push(clone);
    return;
}

const lines = clone.mes.split('\n');
...
ttsJobQueue.push({ ...clone, mes: line });
```

Therefore it already splits on newline paragraphs, but does not protect against a single extremely long paragraph.

## Production simplification requested by user

The user explicitly wants:

- diagnostics to be temporary
- normal plugin runtime to be as small/simple as possible
- avoid duplicating functionality already provided by SillyTavern
- MultiTTS should manage voice internally
- plugin should not require /voices for normal use
- use SillyTavern's queue and paragraph settings where possible
- if a paragraph is short enough, send it unchanged
- only split an individual paragraph/text when it is too long
- choose the maximum only after measurement, not arbitrary guessing
- investigate whether request/preload/caching should be sequential or concurrent

Current design conclusion:

- reuse SillyTavern's native paragraph splitting and playback queue
- do not create a custom playback queue
- do not prefetch multiple MultiTTS WAVs in parallel while current CORS restrictions exist
- further-split only overlong provider inputs
- determine a safe maximum empirically
